# Codex CLI 多任务并发与隔离评估

日期：2026-09-09。范围：真实业务后端接入前的方案研究。已确认需求见 [Product-Spec v0.16](../../Product-Spec.md#92-执行并发安全已确认-p0)，实施顺序见 [DEV-PLAN v1.12](../../DEV-PLAN.md#31-会话生命周期与并发实施约束)。

本机已核对 Codex CLI 0.153.4 的版本与命令帮助，并查阅官方文档。当前业务后端仍未实现；下面的容器、凭据和容量方案是推荐做法，尚未完成 Linux 实机验证。本次没有启动模型生成、进行付费压测或更改运行中的服务。

## 结论

可以围绕 Codex CLI 设计多任务并发执行，但会话 ID 只解决上下文归属。要满足用户“必须隔开”的要求，还要让不同任务无法读取或修改对方的会话文件、图片、临时文件，也不能通过后台接口或共享工具绕过去。

推荐：**一项业务任务保存一份独立会话状态；每轮生成使用一个新的独立执行容器。**本轮结束销毁容器，保存该任务的会话状态和结果；返工时启动新容器，续接原会话。相同任务仍然只能同时执行一轮。

API、任务队列、数据库、对象存储可以由平台统一管理。CLI 容器只拿到这轮需要的材料，图片上传和最终版本提交由可信后端负责。平台允许员工查看共享任务，与 CLI 只能接触当前任务材料是两层不同权限。

## 官方能力与限制

| 已核实的事实 | 对本项目的影响 |
|---|---|
| `codex exec` 支持非交互运行、JSONL 事件以及按明确会话 ID 续接；`--ephemeral` 不保留会话文件。[非交互文档](https://learn.chatgpt.com/docs/non-interactive-mode) | 可以实现“每轮一个进程、同任务续接”。不能用共享的最近会话，也不能给需要返工的任务启用该会话临时模式。 |
| `CODEX_HOME` 包含配置、认证、日志、会话和 Skill 等状态；SQLite 位置还可被单独配置覆盖。[环境变量文档](https://learn.chatgpt.com/docs/config-file/environment-variables) | 每个任务使用独立状态存储；检查 SQLite、日志、缓存是否被配置到共享路径，不能只分工作目录。 |
| 权限配置支持禁止读取其他目录；命令网络规则只有在代理实际启用时才生效，MCP、连接器等另有控制。[权限文档](https://learn.chatgpt.com/docs/permissions) | 默认工作区写权限不能单独作为跨任务保密证明；需要系统隔离，并检查所有启用的工具。 |
| Linux 沙箱依赖 bubblewrap、seccomp 与宿主支持；容器环境可能限制其运行。官方提供容器隔离思路，也提醒容器内可访问的凭据仍可能泄漏。[沙箱文档](https://learn.chatgpt.com/docs/sandboxing)、[安全文档](https://learn.chatgpt.com/docs/agent-approvals-security) | 在目标 Ubuntu 24.04 上验证内外两层限制；不要为了让 CLI 启动而直接给它宿主控制权限。 |
| 官方要求浏览器登录产生的 `auth.json` 按 runner 或串行流程管理，不跨并发作业共享；另一作业先刷新令牌可能让旧凭据失效。[登录维护文档](https://learn.chatgpt.com/docs/auth/ci-cd-auth) | 不能让 N 个 CLI 共用一个可写登录文件，也不能把同一组刷新令牌复制 N 份就认为解决了问题。 |
| CLI 子命令的环境变量可通过明确策略筛选。[环境策略](https://learn.chatgpt.com/docs/config-file/config-advanced#shell-environment-policy) | 后端构造最小启动环境；同时保护凭据文件和进程可见性，仅过滤子进程环境变量不够。 |

## 推荐怎么运行

~~~mermaid
flowchart TD
  U["N 位用户提交任务"] --> API["API：验证身份并保存任务"]
  API --> Q["持久队列：等待执行名额"]
  Q --> W["可信 Worker：认领任务、准备材料"]
  W --> R["受控执行管理：最多 C 个运行任务"]
  R --> A["任务 A · 本轮独立容器"]
  R --> B["任务 B · 本轮独立容器"]
  A <--> SA["仅 A 的持久会话状态"]
  B <--> SB["仅 B 的持久会话状态"]
  A --> RA["A 的输出"]
  B --> RB["B 的输出"]
  RA --> V["后端校验、上传、提交有效版本"]
  RB --> V
~~~

以下是本项目的工程建议，不代表 Codex 已替平台实现：

| 隔开什么 | 建议做法 |
|---|---|
| 会话记录 | 每个 taskId 对应独立 `CODEX_HOME` 及状态卷。一个任务的会话 ID 不能被用于另一个任务；续接前先由数据库检查归属。 |
| 输入和输出 | 容器仅挂载本任务需要的输入、历史材料、本轮输出和会话存储。冻结输入与 Skill 只读；输出按轮次分开。不能把全部任务目录的父目录挂进去。 |
| CLI 配置和工具 | 使用固定版本镜像与受控配置，隔开用户目录、临时目录、缓存、日志和 SQLite。仅加载批准的 Skill/工具，不挂开发者整套 Codex 配置、共享 app-server socket 或个人连接器。 |
| 进程 | 每轮重建独立容器，使用非 root 用户、独立进程空间和限制权限。镜像可复用，其他任务的可写运行状态不能复用。 |
| 网络 | CLI 容器不加入 PG、Redis、对象存储的内部服务网络；只允许实际需要的模型和图像服务出口。外部网络限制覆盖 CLI 整个进程，不能只靠命令代理配置。 |
| 后台凭据 | PG/S3 管理凭据留在可信后端。CLI 的模型凭据也要避免被模型执行的命令读取；必要时使用受控凭据代理，具体方案随认证方式验证。 |
| 资源 | 对整个执行容器限制内存、CPU、进程数和时长；临时文件、日志和持久状态另设磁盘额度。一个任务的全部子进程都计入限制。 |

执行管理组件负责创建和停止容器，可以由受控的宿主服务实现。若需要访问容器运行时，权限仅交给该组件；CLI 容器不挂 Docker socket，不使用宿主网络或宿主进程空间，不接收用户传入的任意挂载路径、镜像或启动参数。

优先保留 Codex 内层沙箱，外层容器负责任务之间的隔离。内层不兼容时应停下验证，不能自动退回宿主全权限运行。普通容器仍共享宿主内核；本建议针对内部业务任务的数据、进程与权限隔离，不宣称达到独立物理服务器的隔离程度。

## 登录方式需要单独选对

**会话独立，不等于登录凭据独立；登录凭据独立，也不等于调用额度独立。**

| 方式 | 评估 |
|---|---|
| CLI 使用 API Key | 官方推荐用于程序化执行，按 API 计费。适合做统一受控的后端认证；仍需保护密钥、限制额度并验证所需图像能力。[认证说明](https://learn.chatgpt.com/docs/auth) |
| CLI 使用工作区服务账号令牌 | 官方提供用于无人值守工作的服务身份，目前只对按量付费计划开放。本项目是否可用尚未确认，不能默认用户已有权限。[服务账号文档](https://learn.chatgpt.com/docs/enterprise/service-accounts) |
| 复用桌面端浏览器登录文件 | 不推荐直接作为 N 路并行执行方案。共享文件有写入竞争，复制同一刷新凭据也有轮换冲突；要继续采用，必须先验证独立登录流和凭据更新方式。[登录维护文档](https://learn.chatgpt.com/docs/auth/ci-cd-auth) |

这里评估的是 CLI 的认证方法，执行器仍然可以是 Codex CLI。本次不替用户购买额度、切换认证方式，也不读取现有登录文件。图像生成会占用相应使用额度；API Key 与 ChatGPT 方案采用不同的计费来源，更多会话不会凭空增加额度。[图像生成与用量](https://learn.chatgpt.com/docs/pricing#image-generation-usage-limits)

## N 个用户与 C 个执行名额

N 是同时提交或查看任务的人数；C 是同时运行的生成轮数。若 N=20、C=4，则在每人提交一个独立任务且队列有空间时，4 个运行、16 个等待。4 只是举例，不是本次确认的配置。

当前架构可以以“20 人同时使用和提交”为实现目标；本次没有足够证据承诺 20 轮真实生成同时运行。C 要综合以下数据确定：

- 可供执行的内存，扣除 API、数据库、存储和安全余量后，再对照整轮执行的峰值内存。
- 图片解码、处理、上传的 CPU、磁盘和带宽消耗。
- 选定认证和图像服务的实际限流、额度及错误情况。
- 用户能接受的排队时长，以及提交高峰是否会持续超过处理速度。

外部服务可能按请求或用量限流，不能将其直接当作固定进程数。一个 CLI 轮次也可能发起多次调用；建议首期关闭自动派生子 Agent，需要时再单独限制，避免 C 个业务任务扩成更多内部执行。[官方配置示例](https://learn.chatgpt.com/docs/config-file/config-sample)

先以 1、2、4 等档位测真实工作负载，前一档通过后再增加。记录完成耗时、峰值资源、队列等待、上游限流与失败率；生成队列应有明确上限，超限时返回可理解的提示。排队名额可以集中管理，但不能让全部任务共用一个会话或一个可写状态目录。

## 后续怎么证明隔离生效

以下均为待执行验证，不是本次通过的测试：

1. 同时运行 A/B：在双方材料中放不同的测试标记，尝试跨任务读取、列目录、修改、通过链接访问，均应失败。
2. 错用会话 ID：把 B 的 ID 用于 A 的返工，后端拒绝；A 的运行环境无法从本地找到 B 的会话。
3. 检查凭据与出口：模型可用工具不能读到 PG/S3 管理凭据；不能通过环境、凭据文件、进程信息或共享工具访问其他任务；不能连接后台服务网。
4. 让 A 超时、内存耗尽或被取消：A 被限制并收尾，B 不被终止、不丢结果；A 的失效结果不能写回。
5. 重建容器：A 首轮结束销毁容器，挂回 A 的持久状态后按原 ID 返工；不会丢记录或续接 B。
6. 制造重复消息和 Worker 中断：一个任务最多启动一份有效执行；旧执行未核实停止前，不因超时或重投再开一份。
7. 验证认证续期：并发过程中认证失效、令牌轮换、服务重启均有明确结果，不能靠反复新建会话绕过问题。
8. 模拟 20 人提交：检查受理、排队、限额、查询与取消。再按 C 的不同档位进行真实图片负载测试，区分 API 接收能力和生成吞吐。
