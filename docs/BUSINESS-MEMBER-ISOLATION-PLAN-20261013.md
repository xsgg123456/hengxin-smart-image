# 国内与海外成员隔离整改方案

日期：2026-10-13。状态：方案待确认，未开发、未部署、未清理生产数据。

## 1. 目标与边界

用户已明确：国内、海外用户不能因为登录而混入对方成员目录。本轮只出整改方案。

推荐方案：继续共用钉钉企业身份认证；两边分别查询权限、分别申请加入、分别由本业务管理员授权，只有进入选定业务时才建立该业务会话。

- 企业身份回答“你是谁”；业务成员关系回答“你被谁批准加入哪个业务”。企业认证成功不等于加入任何业务。
- 国内登录、海外登录、选择页加载、刷新、切换业务和窗口恢复，都不得自动创建另一业务的成员或申请。
- 同一员工可以经两边分别授权而同时成为国内、海外成员。这是合法双业务身份，不能通过“国内有这个人就从海外排除”实现隔离。
- 保持独立数据库、业务角色、会话、审计和资源权限，不新建第二套钉钉登录，不按姓名、部门、IP或国籍猜业务归属。
- 本方案涉及国内与海外两边；只修海外会留下相同的反向问题。

## 2. 已查明的原因与证据

| 位置（相对代码根目录 hengxin-smart-image/） | 当前行为 | 后果 |
|---|---|---|
| `frontend/src/views/auth/IdentityPortal.vue:76` | 加载统一身份后并行调用两边 `access()` | 尚未选择业务就进入两边会话兑换 |
| `frontend/src/api/identity/auth.ts` | `access()` 实际调用 `auth/identity/session` | 权限检查带有建档、发会话或撤旧会话的副作用 |
| `backend/app/overseas/auth/identity.py:17`、`auth/router.py:38` | 先建 pending 成员；拒绝登录仍提交成员 | 国内使用者也可能变成海外待授权成员 |
| `backend/app/modules/auth/dingtalk_members.py`、`identity_bridge.py` | 国内也在认证时建 pending 用户并保留记录 | 海外使用者也可能混入国内目录 |
| `backend/app/overseas/members/service.py:46` | 默认计数海外成员表全部匹配记录 | 自动创建的待授权人员计入成员总数 |

此前隔离复现：成员数 1 → 发起未授权身份的海外会话兑换 → 返回 403，但成员数变成 2；新增记录 pending、零角色、零海外会话；重复兑换不重复建人。后端相关 35 项、前端相关 12 项测试通过，证明现有行为，不代表整改已经完成。本轮未核对生产每个人的来源。

旧 `docs/OVERSEAS-PHASE17-CONTRACT.md` 明确允许入口同时兑换两边会话、未授权身份登记 pending。整改需要覆盖这两条旧约定，不能仅给成员页增加默认筛选。

## 3. 推荐的用户流程

### 3.1 统一登录与业务选择

钉钉认证 → 只读查询国内/海外准入状态 → 显示两个业务入口。

| 本业务状态 | 页面表现 | 是否写业务成员/申请 |
|---|---|---|
| 已授权且启用 | 显示“进入国内业务”或“进入海外业务” | 查询不写；点击后仅建立所选业务会话 |
| 尚未加入 | 业务入口不可进入，旁边提供“申请国内权限”或“申请海外权限” | 只有明确提交申请才写所选业务申请 |
| 申请待审批 | 显示“申请待审批”，允许本人撤回 | 不建正式成员，不发业务会话 |
| 申请被拒绝 | 显示拒绝结果，可重新提交申请 | 只保留本业务申请历史，不自动授权 |
| 已停用或已撤销授权 | 显示“已停用，请联系本业务管理员” | 不允许重新申请绕过停用，恢复由管理员操作 |
| 查询失败 | 显示“连接失败，重试” | 不降级建档，不误报无权限 |

申请仅需用户确认目标业务，姓名及企业身份取自已验证钉钉身份；不增加部门填写或让用户自选业务角色。申请国内权限不能生成海外申请，反之亦然。

已有本业务会话刷新时复用当前会话，只核验身份和权限；同一身份不卸载页面、不丢草稿。直接打开海外地址也不能替用户提交海外申请。

### 3.2 管理员管理

在各自“用户与角色”页内区分“成员”和“加入申请”，沿用既有页面与组件。

- “成员”：本业务已经批准加入的人员，包括启用及保留的停用成员；分页总数与列表使用完全相同的归属条件和筛选条件。
- “加入申请”：只有用户主动提交给本业务的申请，单独计数。管理员批准并选择本业务角色后，事务内建立或恢复本业务成员、记录审计、结束申请；拒绝不建成员。
- 撤回、拒绝和重复提交均有明确结果；已批准申请不得再由申请人撤回成员资格。对已加入人员保留本业务停用及撤销授权路径，撤销本业务会话并保留必要历史归属。
- 国内管理员只处理国内申请；海外管理员只处理海外申请。海外每人一个角色的现行约束保持。
- 不从国内成员列表导入海外成员，不因国内超级管理员身份自动赋予海外权限。

## 4. 后端改动

### 4.1 把三种操作拆开

两边分别提供下列语义，复用已有身份校验和请求防伪机制：

| 操作 | 建议接口 | 允许的业务写入 |
|---|---|---|
| 查自己的业务准入状态 | `POST <业务前缀>/auth/identity/access` | 无；仅按验证身份查本库成员/申请 |
| 进入已获授权的业务 | 既有 `POST <业务前缀>/auth/identity/session` | 本业务会话及已存在成员的必要资料更新；不创建成员或申请 |
| 主动申请加入 | `POST <业务前缀>/auth/identity/application` | 当前验证身份在目标业务的申请，不授角色、不发会话 |
| 查本人申请/撤回 | 本业务 identity application 查询/撤回接口 | 撤回仅变更本人未结束申请 |
| 管理员审批 | 本业务管理申请接口 | 本业务成员、角色、审批审计，同一事务完成 |

业务前缀：国内 `/api/v1`，海外 `/api/overseas/v1`。上述是本项目接口设计，不新增外部服务或第三方依赖。

只读是指业务数据库无新增、更新、删记录，也不签发或撤销业务会话；身份服务仍可消费一次性票据。不得为了更新姓名、最近登录时间而让 access 查询产生业务写入。

### 4.2 票据与会话边界

- 在现有业务绑定的一次性票据上增加用途绑定：access / session / application。身份服务按业务服务密钥和用途校验；查询票据不能拿去申请或登录，国内票据不能用于海外。
- 成员身份必须来自服务端兑换结果中的企业 ID 与钉钉成员 ID；不信任前端传来的姓名、人员 ID、角色或 business 字段覆盖服务所属业务。
- 会话兑换必须再次查当前授权，不能仅信任几秒前的 access 结果。审批、停用与登录并发时以最新授权为准。
- 保留现有安全语义：换号后不能沿用上一人的业务会话；选定业务兑换失败仍撤销当前浏览器所带该业务旧会话。只读 access 不承担撤销逻辑。
- 页面恢复时核对当前统一身份与业务成员归属，不能只比较显示姓名；两位同名员工、跨标签页换号和过期响应必须覆盖。
- 全局退出仍撤销统一身份；本业务停用/退出只影响本业务。不得因修列表改变这两种退出语义。

### 4.3 数据与旧入口

- 国内和海外各自保存加入申请，不建跨库共享成员表；申请记录包含已验证企业/成员标识、申请时间、状态及审批/撤回审计。
- 同一企业成员在同一业务最多一条未结束申请；重复点击、并发批准必须幂等。批准与建立成员/角色在同一事务；以稳定身份去重，不能以姓名去重。
- 新成员记录只由本业务审批或明确的管理员初始化流程建立。移除海外 `bind_member()` 和国内 `authenticate_member()` 在普通登录过程中的自动建档。
- 国内旧钉钉网页回调、容器免登、统一身份兑换必须共同遵守“不因登录自动建人”。旧入口遇到未加入用户，引导到明确申请流程，不能保留旁路。
- 现有启用成员与角色不要求重新申请。已停用人员保留停用，不能因申请或登录恢复权限。
- 海外首个管理员初始化不能再依赖入口隐式生成 pending 成员：由指定企业/成员先明确提交海外申请，现有独立 bootstrap 命令核验该申请与海外配置后建档授权。重复执行不重新提权，已有管理员时拒绝再次初始化。
- 国内已有明确配置的初始化身份沿用显式初始化边界，查询权限不执行初始化；实现前审计国内旧初始化入口，避免失去首位管理员的合法开通路径。

## 5. 历史混入数据整改

先阻断自动建档，再核对历史数据。仅改新登录逻辑不会使截图中的历史记录自动消失。

1. 分别只读导出两边的成员 ID、企业/钉钉身份标识、状态、角色、创建时间、授权审计、会话和任务/文件/归档等引用摘要。报告不包含密码、令牌或密钥。
2. 区分“已有本业务有效授权证据”“有明确本业务申请证据”“来源无法确认”。国内有记录、海外 pending、没有成功会话，都不足以单独认定为误建。
3. 保留已批准或有业务历史的真实成员及所有关联数据；真实双业务人员分别保留。待授权且无角色、无会话、无业务引用的记录只是优先核查候选，不能直接批量删除。
4. 确认的真实待授权申请转入本业务申请区；来源不明的历史 pending 标为 `legacy_unconfirmed`，只在管理员待核对视图出现，不计正式成员、不视作新申请、不获得访问权限。原 ID 与历史引用保留，后续审批可在同身份核验后复用。
5. 确认误建的空记录可按审核名单清理。先输出逐条清单、引用检查及恢复资料，再执行指定 ID；执行前重新核对状态/版本/引用，出现新授权或新业务引用即跳过，禁止按 `status=pending` 一刀切。
6. 完成后验证成员列表、总数、申请数与名单一致；两边原有任务、图片、归档和管理员权限保持可用。数据纠正留审计。

需要独立、可回滚的数据库迁移，为历史记录提供成员归属确认状态；不能只在前端过滤。名单未核对完时，待核对状态可暂存，但不能宣称历史整改已全部完成。

## 7. 必须通过的验收矩阵

| 场景 | 预期 |
|---|---|
| 仅国内授权用户登录并进入国内 | 海外成员数、申请数、会话数均不增加 |
| 仅海外授权用户登录并进入海外 | 国内用户数、申请数、会话数均不增加 |
| 双边均有权限，只进入国内 | 两边原有成员保持；只建立国内新会话 |
| 两边均未加入，只完成钉钉登录 | 两库成员和申请均不增加，两个业务均不可进入 |
| 主动申请海外权限 | 仅海外增加一条申请，正式成员数不增加；未审批不能进入 |
| 审批通过、拒绝、撤回及重复/并发提交 | 仅本业务产生规定结果，成员与角色不重复，失败无半成品 |
| 海外管理员审批国内申请，或反过来 | 拒绝，目标业务数据不变 |
| 国内旧登录、容器免登、直接访问海外链接、旧前端会话接口 | 均不能隐式创建另一业务成员，也不能绕过显式申请规则 |
| 刷新、切回窗口、业务切换、查询故障和请求重放 | 查询不建人、不申请、不轮换会话；票据不能跨用途/业务复用 |
| 两个同名员工、A换B、跨标签页退出/换号 | 不显示或继续操作旧人的业务数据，不按姓名复用权限 |
| 停用/撤权后旧会话，申请重新开通 | 旧会话下次请求拒绝；不能自助绕过停用；另一业务不受影响 |
| 历史未知来源 pending | 仅待核对可见，不计正式成员，不自动成为主动申请 |
| 清理候选在执行前获得角色或业务引用 | 跳过并报告；不删除新授权成员或相关任务/图片 |
| 初始管理员与最后一名管理员 | 显式初始化路径可用，重复初始化不提权，最后管理员保护保持 |

隔离测试要对两库真实记录数和写入结果断言，不能只验证前端按钮禁用。真实企业钉钉与生产数据核对另记证据，不用模拟结果代替。

## 8. 发布与回退注意事项

- 采用兼容的新增表/字段迁移，先备份并演练恢复；后端封住隐式建档与前端新准入流程作为同一发布单元。旧页面遇到协议变化提示刷新，不能为了兼容旧前端恢复自动建档。
- 身份服务用途票据、两业务后端和前端必须核对版本兼容；旧的无用途票据不能自动当作申请票据。发布期间短暂登录失败允许明确重试，不允许副作用降级。
- 历史清理独立于代码上线，默认只出审核报告。数据修正前后均核验两边人员名单和业务引用。
- 回退优先回到仍保持隔离的兼容版本；不得直接回滚到会自动双边建档的旧登录代码。必要时暂时关闭新申请或统一入口，保留已有合法业务会话；不恢复已停用人员权限。
- 本轮仅完成方案。实现、生产发布和名单清理均未执行，且不沿用其他功能的部署授权。
