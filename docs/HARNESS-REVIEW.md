# 审查快照交接协议

本协议替代向 `.codex/.needs-review` 写 `clean` 的旧流程。hook 注册仍由 `.codex/hooks.json` 唯一管理；默认不注册 Stop，结束回复不触发审查阻断。产品需求不因此改变。

## 开发、审查与提交

1. 完成实现、测试、格式化和必要生成文件整理；不要把收尾的代码修改留到审查后。
2. 在仓库根目录执行 `python .codex/hooks/harness.py review-prepare`。输出 `candidateId` 是送审代码快照编号；把编号、范围、源文档和验证证据交给独立 reviewer。
3. reviewer 做两阶段审查，报告记录该编号。失败则修复、重新 prepare，复核新旧差异；主Agent不能擅自判断所有空白修改都安全。
4. 两阶段通过后执行 `review-approve`，JSON 输入包含 `candidateId`、仓库内报告相对路径 `report`、`stage1: "PASS"`、`stage2: "PASS"`。命令支持第二个参数传JSON，也支持stdin输入；调用时正确引用JSON，不把字符串当Shell代码。脚本确认当前内容仍等于候选快照，报告存在，再保存凭据。
5. 用户授权提交后单独 `git add`，再用另一次工具调用执行独立的 `git commit`。提交门禁检查暂存区相对HEAD的受控文件变化是否与凭据一致，再执行现有类型检查。不支持包含commit的复合脚本、`commit -a`或路径提交，避免预检查之后才改写暂存内容。提交参数含Shell表达式或特殊字符时拒绝，复杂说明先写文件再用 `-F`；仅支持 `-C`、`-c`、`--no-pager`、`--no-optional-locks` 全局参数，其余检测到的提交明确拒绝。部分提交可以只包含已审文件，未提交的未审变化仍不能据此宣布完成。
6. 完成交付前用 `review-status` 核对当前内容与批准快照。普通 add/commit 不改变文件内容，不会撤销批准。提交门禁继续检查暂存版本和报告凭据；结束回复不代表审查通过。

## 中途问答与暂停

`review-status` 只读显示当前/批准快照编号、差异文件和是否匹配。

回答中途问题、等待信息或用户要求暂停时，可直接结束回复并说明未完成事项，无需创建 checkpoint。

`stop-gate` 和 `review-checkpoint` 命令保留供旧配置兼容，默认不自动调用。旧配置中的 checkpoint 仍只允许一次 Stop，不批准代码、不影响提交门禁，后续文件修改会使它失效。

## 文件范围、存储与边界

状态保存在Git忽略的 `.codex/review-state.json`，原子写入并串行更新。首次接入使用既有HEAD作为信任基线，不把预先存在的脏改动或未跟踪代码当作已审；基线不等于新生成的审查报告。

快照纳入代码、JSON/YAML/TOML运行配置、锁文件和框架规则；排除依赖、构建、日志、测试输出和运行状态自身。普通Markdown报告不属于代码快照；AGENTS和技能等研发规则需要纳入。文本CRLF/LF归一，不忽略其它空白；符号链接不跟随到仓库外部。

旧 `.needs-review` 与 `.review-snapshot.json` 不再授权放行，保留文件不会影响新协议。迁移时若没有可靠的新批准凭据，未提交代码需要送审，不自动把旧clean转换为批准。

这是Agent协作协议，不是不可伪造签名：脚本核对版本和结构，主Agent仍负责依据真实reviewer结论登记通过。普通终端绕过Codex hook、检查后外部进程竞态等情况仍需CI/服务端保护。本次取消默认 Stop 注册；当前会话是否已重载以运行时状态为准，旧注册仍可使用兼容命令。更新 hooks.json 后按 Codex 信任流程重新审阅。
