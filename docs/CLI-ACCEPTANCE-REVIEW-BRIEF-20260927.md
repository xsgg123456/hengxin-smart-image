日期：2026-09-27。本轮为用户要求的后端验收专项审查；不部署、不修改生产数据、不重新生成图片。以下根治方案为审查建议，不冒充已实现行为。

## 审查目标与步骤

用户目标：Codex 最终交付了成品图片，后端不能因过程中的可恢复异常误判失败。

1. 核对既有产品契约：读取 Product-Spec 中最终回复交付、自动干预、并发与恢复要求。完成标准：区分违反既有契约的缺陷与为满足新目标需要调整的规则。
2. 固定代码快照，独立审查正常执行、自动续接、恢复收图及发布。完成标准：每项问题有代码位置、输入前提与实际结果。
3. 构造对抗案例，核对现有测试盲区。完成标准：已复现、生产实证与仅需防范的协议风险分别记录。
4. 给出统一验收方案和回归矩阵。完成标准：有效交付不被过程噪声否决，同时保留隔离、取消、完整性和幂等约束。

## 第一性原理

业务要获得的是本轮完整、真实、可读取且有权发布的成品。网络重试、计量信息和进程退出属于执行证据；这些信号与图片交付相关，但并不等同于交付结果。

建议将判断拆成三层，而不是用一个 error 字符串替代全部结论：

| 层次 | 回答的问题 | 应保留的证据 |
| --- | --- | --- |
| 执行诊断 | 执行是否结束，发生过什么异常？ | 调用身份、进程状态、终态、错误及用量采集情况 |
| 交付验收 | 本轮是否明确交付完整且有效的图片？ | 最终交付引用、槽位、归属、文件解码、哈希和安全检查 |
| 持久发布 | 是否已安全保存并对用户可见？ | 当前轮次/执行权、取消状态、存储确认、事务和幂等记录 |

历史可恢复错误不得单独推翻后续完整交付。无法确认最终性或归属时，应保留成品证据进入核实流程，不以“文件存在”代替成功，也不立即再次生成。存储暂时失败应恢复保存与发布，不让模型重做已经生成的图片。

### 必须保留的拒收边界

任务取消/删除、旧轮次或失效执行者、跨任务/历史文件、输入冒充成品、目录逃逸/链接、损坏图片、不完整数量及不可消除的槽位歧义，不因最终回复声称完成而放行。平台技术验收通过也不等于视觉质量符合业务要求。

### 必须明确的兼容边界

既有 Spec 要求正常完成且进程成功退出。若要支持“图片已经交付，但尾部断流、退出非零或完成事件缺失”，需增加受限的结果核实流程及相应契约；不能简单删除终态检查。确定文件稳定、引用属于当前调用、生产进程不再写入及执行权有效后，才可决定补收。

## 建议的实施验收矩阵

- 多种重连原因与重试次数，后续成功/失败、完成后的异常分别验证。
- 有效成品与缺失/异常计量信息组合；计量故障不应伪装为生图失败。
- 普通 Markdown 引用变化、中文编号、预览和下载引用同一文件、明确与歧义顺序。
- 正常执行、续接和 Worker 中断恢复，对相同交付证据必须得到一致结论。
- 交付后存储失败、事务失败与重复恢复；保持可补收、不重复创建版本、不重新调用模型。
- 缺图、坏图、旧文件、跨任务文件、取消和失效租约继续拒收。
