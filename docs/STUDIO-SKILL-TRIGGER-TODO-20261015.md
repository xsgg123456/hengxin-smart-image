## 修复方案与验收顺序

1. 同步需求及计划，明确本次两个目标：所选 Skill 用 $name 触发；正确识别已完成的有效 CLI 输出。保留现有执行消息展示，不将隐藏过程卡片或安装 lxml 纳入本次范围。
2. 先修误报：提取脱敏的生产事件样例，核对重复 id 的层级、值是否一致及是否参与身份判断，再设计限定于 CLI 事件的兼容解析。正文消费与最终结算采用一致规则；不得全局放宽共享 _unique_object 或对全部重复键无条件取末值。
3. 完成判定仍校验进程退出、turn.completed、会话归属和最终正文；工具中途失败后正常恢复不应导致整轮失败。真实 turn.failed、非零退出、超时、缺少完成事件和关键身份字段冲突仍不得判成功。
4. 对解析异常保留可定位的内部错误码；页面提示区分平台执行记录解析异常与用户输入错误，不直接透出原始命令、凭据或堆栈。
5. 再改 Skill 拼接，按本文件上文标准覆盖首轮、续聊、未选、切换 Skill；检查实际请求与 CLI 技能发现/加载证据，不能仅凭字符串正确宣称触发验证完成。
6. 验证：脱敏原始事件离线回放；正文完整性和完成状态回归；搜索事件兼容与关键重复字段拒绝对照；Skill 请求拼接与加载验证；相关前后端测试、构建及独立两阶段审查。
7. 发布修复与历史状态恢复分开处理。当前历史轮次不会因为更新代码自动消除失败提示；准备受限恢复方案，重新校验该轮原始记录和会话归属，通过既有结果发布约束修正状态，留审计记录，不重跑模型、不重新计费、不只改数据库状态。具体生产写入在实施发布阶段明确执行范围。
