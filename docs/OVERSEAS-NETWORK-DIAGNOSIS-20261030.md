# 海外图片传输线路排查（2026-10-30）

## 结论

当前主要瓶颈是客户端到该海外服务器的端到端传输路径，伴随高延迟、TCP重传及低单连接吞吐。应用同时存在全尺寸列表图、原图预览重复请求与no-store的放大因素。没有证据表明服务器出口被限制在当前客户端约1—1.7 Mbps的水平，也不能据此认定用户整个宽带只有此速度。

不能从端到端测试区分具体哪一跳、运营商互联或本地接入导致丢包/重传；也未读取云厂商套餐标称带宽。诊断到此不冒称已定位具体运营商设备。

## 路径核实

- FlClash当前配置为rule，第一条规则 `DOMAIN-SUFFIX,qhhengxin.top,DIRECT`，与用户说明一致。TUN开启、sniffer关闭，系统HTTP代理127.0.0.1:7890。
- 因TUN仍开启，curl `--noproxy '*'` 不代表关闭全部VPN软件；域名经fake-IP映射后由DIRECT规则出站。普通HTTP代理端口请求同域名也命中DIRECT，不能把它当成VPN节点测速。
- 真正节点对照：仅对测试curl使用 `--proxy http://127.0.0.1:7890 --connect-to zhitu.qhhengxin.top:443:107.172.161.139:443`，使CONNECT目标为IP并匹配PROXY；TLS主机名和证书校验仍保留，未使用insecure。无需改系统代理、用户规则、配置或服务。
- 当前节点node5.qhhengxin.top在服务器真实DNS解析为107.172.161.139，和网站同机。采样第11、36秒的网站HTTPS连接来自107.172.161.139本机，且已传输约127万字节，证实代理节点回源路径；因此这条节点路线没有提供另一地区的中转出口。

## 同文件分段对照

为了排除应用鉴权/数据库差异，选用生产站点已经公开的同一个1,264,342字节静态资源 `assets/pdf.worker.min-CjEcRF4W.js`，所有客户端请求200且完整传输相同字节数，不启用压缩参数。每条客户端路径顺序测试两轮，避免互相争抢带宽；这是同站点传输基线，不冒充实际图片鉴权接口的完整测速。

## 服务器出口与TCP证据

- 主机eth0 qdisc为fq，采样时backlog为0，overlimits为0；未发现本次Nginx配置中的limit_rate限速。网卡speed为-1，虚拟网卡值不能作为套餐带宽。
- 对Cloudflare官方测速上传端点发送两次各5,000,000字节无敏感内容的合成数据，均HTTP200。耗时0.119091/0.127985秒，上传速度41,984,700/39,067,078 B/s，约335.9/312.5 Mbps。短测只能证明当时该目的地的出口能力，不是长期保底或到中国线路容量。[端点文档](https://github.com/cloudflare/speedtest/blob/main/README.md)
- 110秒eth0采样与客户端测速同时进行，结果在output/bandwidth-server-monitor-20261030.jsonl。观察到出口峰值至少69.3 Mbps，接口drop计数无新增；不能用此推导全路径没有丢包。
- 客户端公网HTTPS连接样本RTT约250—322ms；一条样本bytes_sent=1,028,015、bytes_retrans=89,984，发送队列约594KB，存在重传和积压。重传字节比例不能当作精确链路丢包率；不排除乱序等成因。
- CPU load约1.03/0.93/1.12，没有本次样本对应的CPU饱和证据。

## 影响与建议

1. 更换为独立且到用户所在地链路更好的中转节点，再对同文件比较；当前VPN节点和网站同机，不构成独立中转优化。这里只建议，不改用户规则。
2. 平台列表缩略图、按需加载、复用已取得的完整原图，减少这条慢链路上的重复字节；用户明确要求大图始终使用原图，不采用低清替代预览。原图尺寸、字节、缩放和下载保持。
3. 若需再定位本地接入与运营商段，使用同电脑手机热点对照，或从另一网络测试同文件；本轮未切换用户网络，因此尚未排除本地接入侧影响。

本轮没有改业务代码、线上配置、VPN规则或服务；7200秒调整继续暂停。规则里的旧待审发布建议按用户“暂不处理”保留。
